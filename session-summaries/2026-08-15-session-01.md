## Bugs found and fixed this session (patterns to watch for)

Nearly all of these were small transcription typos:
- `Hero.tsx`: `"opacity - 0"` (spaces inside the class name) instead of `"opacity-0"` — made the crossfade invisible (all slides stayed opaque, last one in the array always won).
- `Hero.tsx`: `min-h[420px]` missing a hyphen (should be `min-h-[420px]`).
- `layout.tsx`: font variable name mismatch — `variable: "--font-kumbh-sans"` in the JS didn't match `var(--font-kumbh)` referenced in `globals.css`, so Kumbh Sans silently wasn't applying to body text.
- `layout.tsx`: `LayoutProps` used without its route type argument (should be `LayoutProps<"/">` — a Next.js 16 helper type introduced by this scaffold's version, not something from older training data).
- `Order.tsx`: bite-hover custom property named `--bite-hover-color` instead of `--bite-bg`, so the CSS default (cream) was always used instead of the intended override — this was for the **v1 (pseudo-element)** bite-hover implementation, now superseded.

## Current unresolved bug — where we got cut off

The bite-hover technique was rebuilt mid-session from a **v1 fake cutout** (a `::after` pseudo-element painted a solid circle matching `--bite-bg`, a color that had to be manually matched per-instance to whatever was behind the button) to a **v2 true CSS mask cutout** (`mask-image`/`-webkit-mask-image` with a `radial-gradient`, animated via a `@property --bite-radius` custom property, so the notch reveals whatever is *actually* behind the element — photo, gradient, or solid color — instead of faking a color match).

After switching to v2 and removing the now-unnecessary `style={{ "--bite-bg": ... }}` props from `Navbar.tsx`, `Hero.tsx`, and `Order.tsx` (confirmed removed correctly in all three files), Brandon reported: **"now the corner notch doesnt do anything."** I had just re-read all four relevant files (`globals.css`, `Hero.tsx`, `Navbar.tsx`, `Order.tsx`) to diagnose when the session was interrupted for this handoff — **no fix has been identified or applied yet.**

Current `globals.css` bite-hover block (as of end of session):
```css
@property --bite-radius {
  syntax: "<length>";
  inherits: false;
  initial-value: 0px;
}

@layer components {
  .bite-hover {
    --bite-radius: 0px;
    mask-image: radial-gradient(
      circle at calc(100% + 0.4rem) -0.4rem,
      transparent var(--bite-radius),
      black calc(var(--bite-radius) + 1px)
    );
    -webkit-mask-image: radial-gradient(
      circle at calc(100% + 0.4rem) -0.4rem,
      transparent var(--bite-radius),
      black calc(var(--bite-radius) + 1px)
    );
    transition: --bite-radius 0.25s ease;
  }

  .bite-hover:hover,
  .bite-hover:focus-visible {
    --bite-radius: 0.9rem;
  }
}
```

This looked syntactically correct on inspection, so the bug is likely one of:
1. **Masking mode.** CSS mask gradients can default to luminance masking in some browser/spec interpretations rather than alpha masking. If so, the `black` stop (0 luminance) could behave unexpectedly. Try adding `mask-mode: alpha;` / `-webkit-mask-mode: alpha;` explicitly to force alpha-channel masking (transparent = hidden, opaque = shown, regardless of color).
2. **Tailwind v4's CSS pipeline.** Tailwind v4 processes `globals.css` through its own build (Lightning CSS under the hood via `@tailwindcss/postcss`). Worth checking browser DevTools → computed styles on a `.bite-hover` element to confirm `mask-image` is actually present and non-empty, and that `--bite-radius` visibly changes between rest and `:hover` states. If the property is missing entirely, something in the build pipeline may be stripping or mishandling `@property` or the mask declarations.
3. **Stale dev server / cache.** Worth a hard refresh and/or restarting `npm run dev` before assuming it's a real code bug — hasn't been ruled out.
4. **Browser support.** `@property` + animating custom properties needs a reasonably modern browser (Chrome/Edge, Firefox 128+, Safari 16.4+). Confirm which browser Brandon is testing in.

**Next session should start here**: open DevTools on a `bite-hover` element (e.g. the Navbar's "Call Now" button), inspect computed `mask-image`, and check whether `--bite-radius` actually changes on `:hover` in the computed panel. That'll tell us whether the mask is inert or just invisible for a rendering reason.
