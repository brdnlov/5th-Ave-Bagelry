## Framework findings (verified against bundled docs / compiled CSS — do not trust training data here)

- **`priority` is DEPRECATED in Next 16** (`next/image`), replaced by `preload`. Docs at `node_modules/next/dist/docs/01-app/03-api-reference/02-components/image.md`.
- For **CSS-hidden responsive image variants**, the docs say explicitly: *"You cannot use `preload` or `loading="eager"` because that would cause both images to load. Instead, you can use `fetchPriority="high"`."* Default lazy loading is what stops the hidden variant downloading.
- Now that there is a single storefront image at every viewport (one LCP candidate), `preload` **is** correct, and it emits a real `<link rel="preload" as="image">`.
- **Tailwind v4 generates spacing utilities dynamically** — `w-30`, `w-35`, `rotate-4` all compile (`calc(var(--spacing) * 30)`). These do NOT exist in v3's fixed scale. Verified by compiling with the postcss plugin.
- **Tailwind precedence is CSS source order, not class-attribute order.** `.hidden` is emitted at byte 12497 and `.inline-flex` at 12576, so `inline-flex` always beats `hidden` no matter how you type them. **Rule: an element using `hidden` for responsive visibility must have its visible display breakpoint-prefixed** (`hidden md:inline-flex`), never a bare one. This caused a real bug — the desktop "Call Now" button appeared on mobile.
- `transition-transform` in v4 correctly covers `transform, translate, scale, rotate`, so v4's separate `translate`/`rotate` properties do animate.

## Navbar work

Brandon reported "the dropdown is not functioning correctly" at 320–425px. CDP measurement showed the logic was fine (`aria-expanded` toggles, no horizontal overflow) — the problem was physical:

- Hamburger button was **24×18px** (just the three bars, no padding). Now `min-h-12 min-w-12 p-2 -mr-2` → 48×48.
- Dropdown links were **70×23px**. Now `block px-6 py-2 text-lg` → 44px tall. `block` is required, or vertical padding does not count on an inline element.
- Mobile "Call Now" sat **6px tighter** than the other items (measured painted gaps `[24, 24, 24, 18]`). Cause: it was `display: inline`, so its padding painted but did not affect layout, and the pill bled ~6px above its `<li>` box. Fixed with `inline-flex`.
- **Dropdown no longer pushes the hero down.** It was a normal-flow sibling inside the sticky header, growing it from 80px to 376px on open. Now `absolute inset-x-0 top-full` (plus `shadow-lg`, since the dropdown and hero are both `brand-cream` and it otherwise merged into the page). Verified: `hero moved 0px, image moved 0px` at 320/375/425. This works because `position: sticky` is non-static and therefore establishes a containing block.

## Button size audit (industry standards)

Measured every `a`/`button`. Standards: Apple HIG 44×44pt, Material 48×48dp, WCAG 2.5.5 (AAA) 44×44, and **WCAG 2.5.8 (AA) 24×24** — the last is the one that actually fails audits.

Found and fixed: navbar Call Now (both instances) 40px, Order buttons 40px, and desktop nav links at **20px tall, which failed WCAG AA**. Standard recipe adopted: `inline-flex min-h-12 items-center rounded-full px-6 py-3` = 48px. Desktop nav links got `inline-block py-3` = 44px.

**Bite-mark inconsistency explained:** `--bite-radius` is fixed at `1.3rem` (20.8px), but buttons were 40px vs 48px tall, and `rounded-full` makes each corner radius half its own height (20px vs 24px). The same absolute notch against different curvature reads as a different bite — on the 40px buttons the notch radius actually *exceeded* the corner radius, so it looked like a chunk missing rather than a bite. **The fix was to standardise all pills to 48px**, which makes the fixed notch consistent for free.

`.bite-static` (the always-on notch built for the mobile hero photo) was **removed from `globals.css`** — Brandon decided not to use it anywhere. `globals.css` now contains only the palette/`@theme` block, `.bite-hover`, and the `float` keyframes.
