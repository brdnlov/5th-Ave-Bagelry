## The bite-hover saga — this is the important part for next session

### Round 1: CSS-level fix (turned out incomplete)
Session 1 left the mask using `black` as the "visible" stop, which is ambiguous under different masking modes (luminance vs. alpha) across browsers. Fixed by:
- Swapping `black` → `white` (correct under both interpretations)
- Adding explicit `mask-mode: alpha` / relying on `-webkit-mask-source-type: alpha` (Lightning CSS's autoprefix output)
- Adding `mask-repeat: no-repeat` and `display: inline-block` (anchors are inline by default, which can make mask box-sizing unreliable)

Brandon reported this still didn't work.

### Round 2: found the real bug — geometry, not CSS
Rather than guess again, this session used **headless Chrome via the DevTools Protocol** (no Playwright install needed — Chrome was already on the machine at `C:\Program Files\Google\Chrome\Application\chrome.exe`) to:
1. Fetch the actual Tailwind/Lightning-CSS-compiled output from the dev server and confirm the mask CSS was compiling correctly (it was — `@property` registered, `mask-mode: alpha` present, gradient correct).
2. Use `CSS.forcePseudoState` and real `Input.dispatchMouseEvent` mouse moves to force `:hover`, then screenshot before/after and pixel-diff them.

This revealed the actual problem: **all three bite-hover buttons used `rounded-full` (pill shape)**. A ~40px-tall pill has a border-radius of ~20px, which curves the corner away well before the mask's 0.9rem (~14px) notch radius ever reaches a rendered pixel — the notch was carving into space the pill's own curve had already made invisible. Pixel-diffing confirmed the mask was technically firing (a ~5×5px change), just far too small to notice.

Fix: switched buttons to `rounded-lg` and enlarged/repositioned the mask (radius up, offset the circle's center closer to the box corner). Re-verified with the same screenshot pipeline — a clearly visible notch appeared on hover for all three CTAs (Navbar "Call Now", Hero "Order Now", both Order cards' "Order Now").

### Round 3: Brandon wanted pills back
Mid-verification, Brandon asked for pill buttons again (`rounded-full`), which reintroduces the exact swallowing problem above. Rather than just reverting, the mask was **redesigned**: tried centering the bite on the rounded right edge (`circle at 100% 50%`) instead of the corner — this works well geometrically regardless of border-radius since it doesn't depend on a sharp corner existing at all. Was mid-verifying this via screenshots when Brandon said to stop taking screenshots and put the bite back on the corner specifically (not the edge), pill shape kept.

Final design implemented (not re-screenshotted after this point, per Brandon's request to stop the screenshot loop): corner-positioned mask, sized to reach past a pill's own curve mathematically (radius large enough that `radius − offset_distance` exceeds the pill's own corner-curve start distance, which is roughly `0.293 × border-radius` for a rounded-rect at 45°).

### Round 4: "the bite doesn't seem to be getting deeper as I drop the number"
Brandon had been hand-editing the mask's **offset** value (`calc(100% + X) Y`) trying to deepen the bite, with little effect. Explained why: the offset only nudges the circle's center a fraction of a rem outside the corner — it's a fine-tune, not the depth control. **`--bite-radius` (the hover value) is the real depth lever**, since notch depth ≈ `radius − offset_distance`, and radius dominates that formula by an order of magnitude. Bumped `--bite-radius` hover value `1.25rem` → `1.6rem` and reset the offsets to be symmetric (`0.1rem`/`-0.1rem` — they'd drifted to an asymmetric `0.05rem`/`-0.15rem` from manual edits).

## Current state of `globals.css` bite-hover block (end of session)

```css
@property --bite-radius {
  syntax: "<length>";
  inherits: false;
  initial-value: 0px;
}

@layer components {
  .bite-hover {
    --bite-radius: 0px;
    display: inline-block;
    mask-mode: alpha;
    -webkit-mask-repeat: no-repeat;
    mask-repeat: no-repeat;
    mask-image: radial-gradient(
      circle at calc(100% + 0.1rem) -0.1rem,
      transparent var(--bite-radius),
      white calc(var(--bite-radius) + 1px)
    );
    -webkit-mask-image: radial-gradient(
      circle at calc(100% + 0.1rem) -0.1rem,
      transparent var(--bite-radius),
      white calc(var(--bite-radius) + 1px)
    );
    transition: --bite-radius 0.25s ease;
  }

  .bite-hover:hover,
  .bite-hover:focus-visible {
    --bite-radius: 1.6rem;
  }
}
```

## Diagnostic tooling notes (useful if this recurs)

- Headless Chrome + CDP is a solid way to get an authoritative answer on "is this CSS actually rendering" without installing Playwright: launch with `--headless=new --remote-debugging-port=9222`, connect via the `webSocketDebuggerUrl` from `http://localhost:9222/json/version`, drive it with plain `Send`/`WebSocket` JSON-RPC (Node 22+ has a global `WebSocket` client, no deps needed).
- `DOM.getBoxModel` coordinates ARE viewport-relative (they update correctly after `DOM.scrollIntoViewIfNeeded` + a real wait) — earlier confusion in-session about this turned out to be a stale-timing issue, not a coordinate-space issue.
- `CSS.forcePseudoState` and a real `Input.dispatchMouseEvent` mouse-move produce identical rendering — both are valid ways to test `:hover` state.
- Remember to kill the dev server (`netstat -ano | grep LISTENING | grep :3000` → `taskkill //PID <pid> //F`) and the headless Chrome process (same pattern on `:9222`) when done — `lsof` isn't available in this Windows/git-bash environment.
